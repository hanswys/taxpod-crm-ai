## Candidate examples for AI_USAGE.md

Note anything that would make a good "real example": the AI got something wrong, you had to correct a design, or a prompt worked unusually well.

- **Contact delete behaviour (M0).** AI recommended hard delete with cascade as simplest. I asked whether archiving (soft delete) was more realistic; AI agreed (real CRMs use a recycle bin; PDPA still needs a hard purge) and laid out its real cost (filters on every query, archived contacts' opportunities in dashboard totals, restore UI). Kept cascade for scope; moved archive design to "What I would do differently". Example of using AI to weigh a trade-off rather than just accept its default.
- **Planned model retired on day one (M0).** The plan said `gemini-2.5-flash`, flagged "verify model IDs in M0" as a risk, and built `check:gemini` to list models. It returned 404 "no longer available to new users"; the suggested replacement (`gemini-3.8-flash`) was overloaded (503). AI probed each Flash model with retries off and picked the one that answered. Good example of planning for a known AI-tooling weakness (knowledge cutoff) instead of trusting the model's memory.
- **Bug found by looking, not by tooling (M0).** lint, typecheck and build all passed, but a screenshot showed a serif font: shadcn's init had written a self-referencing CSS variable. Shows why "verify in the real app" matters with AI-generated scaffolds.
- **Asking the AI to re-explain its own plan simply (M1).** The first M1 plan listed five open decisions in dense table form. Asking for "explain simply one by one each decision and the choices" got a plain-language A/B/C per decision, which made it quick to approve all five. Useful pattern: make the AI restate a decision list before approving it.
- **Framework knowledge vs bundled docs (M1).** Next 16 changed `error.tsx` (`retry` instead of `reset`) and needs a `loading.tsx` per route for instant navigation with Cache Components. The AI's first draft used the old API and a single root boundary; reading `node_modules/next/dist/docs` and a real browser run (dev-server warnings) caught both. Lint/typecheck/build alone did not catch the second.
- **Search results pointed to stale tax documents (M2).** Web search for the e-Invoice guideline returned links that were 404 or two versions old (v4.6); the official LHDN listing page had v4.8. Caught only because the planning spike actually downloaded and opened each PDF. Led to committing the PDFs with version + date in a manifest rather than downloading at ingest time.
- **First chunker design was wrong; the data said so (M2).** The AI's first heading detector used plausible patterns (numbered short lines, ALL CAPS, Title Case). Lint and types were fine, but printing the detected sections per document showed list items like "1. API Application Programming Interface" becoming sections and the e-Invoice Guideline shattered into 388-char chunks. Switching to the documents' own tables of contents as the source of headings fixed it and deleted most of the heuristics. Then an automated check (every chunk's paragraphs must appear on its cited pages: 0 misses of 497) replaced eyeballing. Shows the value of inspecting intermediate output rather than trusting code that looks reasonable.
- **The answer was faithful, and still wrong (M3).** "Is service tax charged on legal services?" got a well-cited answer quoting a 6% rate from the 2021 SST guide. Before writing "the rate has since changed" into ARCHITECTURE.md, the AI checked the claim against the knowledge base itself rather than its own memory, and found the 2026 Management Services guide (p. 5) saying 6% → 8% from 1 March 2024. Good example of grounding working as designed (it only used what it retrieved) while showing the next problem: conflicting sources of different ages. Became an M4 eval case.
- **Free-tier limits found by testing, not docs (M3).** Planned: one fallback model for 503s. Testing showed both Flash models failing together, a 5/minute limit, and a 20/day limit, plus the SDK retrying 429s (spending quota). The 429's "retry in 16h17m38s" also broke the first parser, which only understood seconds. Changed the fallback to a Flash-Lite model with its own quota and stopped SDK retries on 429. Shows why the plan said "verify limits at build time".
- **A lenient eval scored the most important bug as a pass (M4).** The draft question "What is the current service tax rate on legal services?" accepted either SST guide, so retrieval scored 10/10. While checking the conflict fix, the AI listed the actual top 10 and saw the passage with today's 8% rate at rank 9, outside the 6 the model read; the hit came from the outdated 2021 guide. It tightened the expected source, the score dropped to 9/10, and the fix (k = 10 + dated sources) became measurable. Lesson: an eval's "expected source" has to be the source of the *right* answer, and aggregate numbers need a look at the per-question rankings.
- **An experiment that quietly measured the wrong thing (M4).** The rerank mode was written to fall back to vector order if the Gemini call failed, sensible for the live app. On the first eval run every call hit a 503, so the "rerank" results would have been identical to vector, which reads as "rerank doesn't help". Spotted from the log warnings, not the numbers. The eval now runs rerank in strict mode (fail instead of fall back). Same code, different correct behaviour for production vs measurement.
